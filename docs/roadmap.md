# 增量开发计划与验收

2026-11-16 修订。采用增量设计、阶段性交付；完整架构作为长期参考，本文件定义当前实施顺序。v0.0/v0.1 已实现，完成 API pilot、本地GPU推理与八轮增长诊断；v0.2 及后续尚未实现。当前运行说明见 getting-started.md，验证范围见 validation-v0.1.md。

用户最新优先级：先把固定权重的harness evolution效果做稳定，再启动其他扩展。当前仅推进[记忆harness backbone](harness-backbone.md)，LoRA、RL和新任务扩展均后置；下表后续版本不表示当前已授权并行启动训练。

每次只增加一个主要变化来源，先得到可运行、可检查的结果，再进入下一阶段。估算按一名熟悉 Python/LLM 的主开发者计，是开发工作日范围；不含资源排队或未知环境故障。

## 1. 版本顺序

| 版本 | 目标 | 本阶段新增 | 通过条件 | 粗估工作量 |
| --- | --- | --- | --- | --- |
| v0.0 | 能执行和评估一个 Task Agent | 一个模型入口、一个任务、固定 prompt、规则评分、结果文件 | 真实小集合可运行，逐题结果与汇总正确 | 1–2 天 |
| v0.1 | 最小自我改进循环 | 固定模型，Meta 每轮提出一个 prompt/受限 harness 配置候选，评估后选择 | 连续运行 3 轮；决策、失败、用量和版本可追溯 | 2–3 天 |
| v0.1b | 文献任务与稳健选择 | 记忆分类harness、固定数据角色、重复评测与预算对照 | 三次搜索分别有正测试增益，按题聚类95%区间下界>0；强基线与随机对照另报 | 1–3 天 |
| v0.1c | 多步工具交互 | ToolHop adapter、固定工具执行、答案与路径评分 | 先验证固定策略，再运行harness-only对照 | 2–4 天 |
| v0.2 | 最小模型–harness 共演化 | 成功轨迹采集、LoRA SFT、导出、重载与下一轮 | 真实权重更新后进入下一轮执行和提案证据 | 3–5 天 |
| v0.3 | 检验跨任务通用性 | 用已接入的S2D与ToolHop整理接口；ALFWorld后续可选 | 两任务共享主循环；执行、评分和训练职责清楚 | 3–5 天 |
| v0.4 | 支撑具体研究课题 | 每次只加 evaluator、数据配比或预算分配中的一项 | 与上个稳定版本做同协议对照 | 按课题拆小迭代 |
| 后续 | 扩大改进或训练能力 | 代码级 harness 编辑、GRPO、历史继承、种群、self_meta 逐项加入 | 各自通过运行、兼容性和预算验证 | 单独估算 |

先争取在 3–5 个开发日内交付 v0.0 + v0.1，再用独立阶段接训练。若模型服务/训练环境尚未就绪，报告具体阻碍，不能把模拟循环当作真实版本完成。

v0.1 只有 harness/config 改进，没有权重训练；v0.2 才交付受限 harness 与权重共同更新。固定外部 Meta 的模式与 self_meta 分别记录。

## 2. v0.0：先验证 Task Agent 与评分

第一个任务采用 GSM8K 小集合，先做单次生成与数值答案评分。模型通过一个已配置的端点访问；本地 serving 和四卡调度不成为主循环实现的前提。

本阶段只完成：

1. 读取任务输入，固定来源版本和样本 ID；答案仅给 evaluator。
2. 用固定 prompt 调用 Task 模型，记录实际输入、输出、生成设置、用量、耗时和错误。
3. 逐题评分并产生固定格式汇总。
4. 保存配置、模型标识、prompt 内容及评分规则标识。

先检查正确答案、错误答案、无法解析和超时，再跑真实小集合。本阶段没有 Meta、训练或工具执行，是基线运行器。

## 3. v0.1：第一条最小自我改进循环

固定 Task 模型、任务、开发样本、评分规则、单题调用预算和选择规则。当前Meta仅修改求解策略system prompt，回答格式合同保存在固定Task用户后缀；不执行生成的任意 Python。

采用固定外部 Meta 模型。Meta 与 Task 是两个逻辑角色；每轮一个子候选，串行执行，不建立种群或历史父代搜索。

当前首选组合是 Claude Code CLI 作为 Meta 的 proposer harness，Task 使用自研薄执行逻辑。v0.1 的 Meta 只接宿主提供的证据并输出结构化候选，Task 先保持单次生成；角色、模型与执行边界见[选型决策 D12](decisions.md)。

~~~text
评估父代 H0，记录基线
对 r = 1..3：
    Meta 读取开发侧执行记录与当前 harness
    提出一个子候选 H_child
    校验可编辑字段和宿主资源上限
    在相同开发样本/推理协议下评估子候选
    开发分数严格改善且满足预算 → 接受
    否则 → 保留父代，记录原因
    用本轮执行和决策记录继续下一轮
冻结最终选择，运行独立 held-out 评估
~~~

严格改善是早期工程选择规则，不等于统计显著改进或泛化结论。平局、退化、无效提案和超时均留记录；允许三轮都不接受子代。

父代评估只有在模型、prompt、数据、生成参数、评分协议完全一致时才可复用。研究随机生成收益时另设重复测量。

### 最小实现

建议先保持少量、平坦模块：

~~~text
src/rsi_base/
  types.py          # 少量明确的输入/输出结构
  agent.py          # 模型调用与 Task 执行
  benchmark.py      # 首个任务数据与规则评分
  improve.py        # Meta 提案与字段校验
  loop.py           # 串行评估—改进—选择和记录
  cli.py            # 薄入口
~~~

按真实逻辑分文件，不先建占位插件。模型调用细节与主循环分离；评分不嵌入 Meta 或模型 client。

运行目录使用 JSON/JSONL，包含 run.json、每轮的候选配置/输入输出/评分/选择/成本，以及 final 目录。模型标识、prompt/config 内容或哈希、任务 ID 和调用记录必须可关联。

通过原子完成标记从已完成轮次恢复；被中断的调用记为未确认，不承诺外部调用的 exactly-once。SQLite、通用 ArtifactStore、算子 DAG、分布式任务和并行调度后置。

### 第一版就保留的边界

- 开发与最终 held-out 集合独立，最终结果不回流本次改进。
- 评分与划分由宿主固定，Task 输入不含 reference answer。
- 固定轮数、调用次数、输出长度和超时上限；调用和重试记账。
- 候选有独立版本，拒绝/失败不覆盖父代。
- 日志不存密钥，中断后保留已有记录。
- 模拟器用于 CPU 检查；真实运行单独标明。

## 3.1 下一增量：按文献选择有实际harness空间的任务

八轮数学实验出现开发增长，但独立结果未确认稳定泛化。按[文献设置核查](research/harness-benchmark-setups.md)已独立实现Meta-Harness参考的记忆分类机制，固定小模型、标签合同、记忆来源与计算预算，开放记忆/检索/上下文策略。S2D参考200/50/212经过重复清理后测试211；该小选择集的增长未泛化，因此新协议使用200/300/291。旧设计配置保留为设计，当前可执行配置见README。

训练反馈、候选选择与最终测试分别隔离；候选重复评估，报告固定策略、同候选数随机搜索与实际成本。先做5轮×2候选，区分标准起点的基础收益与超过最强固定策略两种结论。当前先完成这一阶段；ToolHop与下方LoRA闭环后置，不根据最终测试继续调参。

## 4. v0.2：接最小训练闭环

以已验证的ToolHop任务起步，沿用固定的候选预算、选择协议与串行实验节奏，只加入一个 LoRA SFT learner。使用官方引擎，通过少量作业输入/输出交接，不复制论文实现。

~~~text
(Wt, Ht)
    → 编辑/选择 H_new
    → 在 H_new 下执行训练侧任务
    → 固定 verifier 筛选成功轨迹
    → LoRA SFT 得到 W_new
    → 导出并重载 W_new
    → 确认 (W_new, H_new)，接受或保留父代
    → 下一轮
~~~

只用当前 harness 的成功数据，不混历史回放或合并 checkpoint。成功样本不足时明确 NO_UPDATE。

验收集中在新增训练接口：

1. 训练与开发/确认/最终集合分开，开发和测试轨迹不进入 SFT。
2. 样本匹配实际模型输入，监督范围正确。
3. adapter 确实更新，导出物可加载，后续调用使用新 ModelRef。
4. model–harness 组合一起保存和确认，退化恢复父组合。
5. 生成、训练、重载和评估成本都有记录。

先完成一个短训练作业，再做 2–3 轮。训练和推理分时运行，四卡的使用方式由显存实测决定，不为用满四卡引入复杂调度。

v0.1 的 harness-only 是现成对照；同时保留 Static，加入最小 weight-only 配置。正式多 seed、全面消融与大数据预算在稳定后做。

## 5. v0.3：用两个用例整理接口

用已接入的S2D和ToolHop，检验记忆、工具/动作、episode终止和不同评分带来的变化。根据实际差异再整理benchmark、model、learner协议与目录；需要有状态环境时再单独接ALFWorld。

ToolHop先提供受信任的固定交互loop，保留受限配置编辑。若要让Meta修改可执行harness代码，另开小阶段，在隔离执行、协议smoke与宿主评分/权限边界就绪后开放。

验收包括：两任务共享主循环；评分替换不改变 Task 执行；训练可以关闭并回到 harness-only。长期架构中的注册表、资源对象和存储服务按实际复用点引入。

## 6. v0.4 之后：一次只开一条研究线

| 当前课题 | 下一个最小增量 | 对照 |
| --- | --- | --- |
| evaluator | 固定候选池/轨迹，替换候选评分器并离线重评分 | 固定 gold 下的误选、regret 与评分成本 |
| 效率 | 保持算子不变，改变何时做 H 或 W | 固定交替 vs 预算分配，总资源记账 |
| 泛化 | 冻结 W/H，加入新任务/模型配对或兼容回放 | 单接口训练 vs 新机制，匹配数据/推理预算 |
| RL | 只替换 SFT learner，先验证 token/logprob/分组 | 已稳定的 RSFT 基线 |
| 代码级 harness | 扩大编辑空间，加入隔离执行 | 受限配置编辑基线 |

不把多个新机制打包进同一版本。种群、权重合并、技能库、self_meta 和异步执行分别排期。

## 8. 交付与停止条件

每阶段单独提交并同步 GitHub：可执行代码、一个最小配置、实际验证说明和 progress。大数据、权重与完整运行结果留在外部，Git 保存必要 manifest 和摘要。

阶段完成看行为证据，不看类或文件数量，也不强制分数上涨。失败先在当前范围定位，只有实际需求要求才增加基础设施。

本地小模型已完成GPU推理和增长诊断。先验收记忆harness的独立测试与对照结果，再确定下一增量；不会在本阶段自动启动LoRA训练。
