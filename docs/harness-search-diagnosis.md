# 当前演化没有超过强对照：现有记录诊断

以下描述针对修复前的已冻结版本。新增源码/完整开发轨迹工具、沙箱检索代码与请求去重已进入[工具化演化版本](harness-agent-v1.md)；其效果单独实验，不更改这里的历史证据。

当前方法没有完成“稳定优于强固定harness和随机搜索”的目标。本次回查确认了搜索实现中的具体问题；它们需要修正，不能把失败直接归结为harness演化困难、模型弱或benchmark没有空间。

这是对已冻结搜索的事后工程诊断，不是修复后的性能实验，也不能单独证明每个问题造成了多少准确率损失。没有重新调用模型或打开最终测试记录，原分数与实验产物保留。

## 1. Meta目前只生成配置，无法检查或修改源码

当前Claude Code调用设置了空工具集`--tools ""`。Meta收到预设字段schema、机制的文字说明、父代配置和反馈，但没有harness源码和Task实际渲染的完整输入。它不能运行小样例、调试候选或实现新的检索/重排逻辑。

因此现阶段是固定手写工作流上的参数/prompt搜索，和能读代码、运行任务、修改候选harness的编码agent存在明显能力边界。最小执行闭环已经接通，但优化端被限制得过窄。

一个具体误解：强起点seed2026的第五轮提案认为开启`label_hints`可以让模型看到完整标签集合。然而`MemoryHarness.render`在所有版本的输入头部都已列出完整标签，`label_hints`只增加前几个检索投票建议。这反映Meta的字段理解没有充分对齐实际执行。

## 2. 反馈不足以调试失败的候选

虽然宿主每轮有64条训练内LOO诊断，实际传给Meta的是最多8个错例、2个对例，以及这些样本使用的有序训练记忆。选择集只提供汇总分数。Meta没有收到新候选相对父代的逐题优化侧得失、完整实际输入与失败步骤对比。

| 强起点seed | 轮数 | 不同训练诊断反馈份数 |
| --- | ---: | ---: |
| 42 | 5 | 2 |
| 123 | 5 | 1 |
| 2026 | 5 | 1 |

后两次搜索的父代没有更新，所以五轮训练诊断完全相同。候选失败后，Meta主要新增的是总分与提案历史，而不是帮助定位候选为什么失败的调试证据。完整父代轨迹已经保存在本地，但反馈构造没有把全部必要信息传过去。

修正应先增加优化/训练侧的源码、实际模型输入、父子轨迹对比和有覆盖性的失败采样，继续保持最终测试不回流；不是把最终测试错误直接交给Meta。

## 3. 部分局部候选没有改变任何实际模型输入

对标准起点三次搜索的15个局部候选，发现6个候选与当轮父代的全部900个验证请求完全相同（300题×3次）。根据调用账本，这6个候选仍新发起了5,400次Task调用。

- seed42第2至5轮：覆盖布局已经给出各标签代表例，当前局部数量/类别上限变动没有改变最终输入。
- seed2026第2、3轮：对比成对布局中，示例数量7与8在这些样本上生成了相同输入。

现有规范化只处理了部分无效字段，未完整处理布局与字段的组合语义，也没有在评估前按实际请求去重。相同请求重新推理还会出现少量分数波动。

**这6个候选均未通过接受条件，没有制造已报告的增益。** 强起点实验也未发现这种全输入相同的候选。因此这是已确认的预算浪费与实现缺陷，不能把强起点失败全部归因于它。

## 4. 有限提案过于集中，随机搜索反而探索到不同配置

每次5轮中，每轮只有1个Meta提案，另1个是硬编码局部邻居。局部邻域主要切换流程、数量±1、类别上限、顺序和提示，不搜索检索算法。

强起点三次搜索共15个Meta候选，**15个全部保留BM25**；大量改动集中在prompt与8附近的示例数。随机搜索至少在两个seed选到了不同的组合，例如TF-IDF/21例，或BM25/12例加查询改写。标准起点的14个有效Meta候选也只有1个尝试hybrid，其余13个为BM25。

这支持“探索不足”的诊断，也表明当前空间至少有可尝试的候选，不能仅用模型能力或任务天花板解释停滞。不过修复后的Meta是否能稳定优于随机搜索，仍需受控实验验证。

## 下一次小迭代的优先级

1. 让Meta看到源码、渲染后的实际输入，并能对优化样例检查候选的具体成败。
2. 补齐有效策略判定与请求去重，避免无执行变化的候选消耗预算或因推理波动获益。
3. 把失败候选的优化侧轨迹反馈回来，改进探索，而不只重复父代的同一批错例。
4. 固定Task模型、评分和训练权重，先在开发侧验证对强固定策略与随机搜索的优势；旧测试只作历史回放，独立验收另行封存。

这次没有通过换弱起点、追加测试轮数或更新模型权重来宣称成功，也没有把上述建议写成已实现或已验证的收益。

## 证据与重现

[机器可读诊断](validation/memory-search-diagnosis.json)只包含候选编号、计数、选择集汇总及输入是否一致，不包含原始题目或模型输入文本。需要原始本地run才能重新计算输入一致性；不需要GPU或API凭据：

```sh
.venv/bin/python scripts/diagnose_memory_search.py --output runs/memory-search-diagnosis.json
```

该检查只对父子均为单调用`direct`的候选比较完整请求；没有把多步流程中的首步相同误判成整个harness等价。
